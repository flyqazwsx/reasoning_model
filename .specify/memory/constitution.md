# Reasoning Model 專案憲章

## 核心原則

### I. TDD-First（不可妥協）

**測試驅動開發是本專案的基石，必須嚴格遵守。**

- **紅-綠-重構循環強制執行**：所有功能與缺陷修復必須依序為：撰寫失敗測試 → 最小實作使其通過 → 重構
- **測試先行，實作在後**：撰寫任何實作程式碼前，MUST 先有失敗的測試，並親眼確認其因正確原因失敗
- **缺陷修復先重現**：修 bug 前 MUST 先寫出能重現該 bug 的失敗測試
- **使用者驗收測試前置**：驗收測試須經使用者或產品負責人同意後，才能開始實作
- **覆蓋率要求**：新增或修改的程式碼測試覆蓋率 MUST ≥ 90%（以 `pytest --cov=src` 量測）
- **測試即文件**：測試名稱與結構必須清楚表達行為意圖（Given / When / Then）
- **禁止繞過**：不得以跳過（`skip`、`xfail`）、刪除或放寬斷言來讓測試通過

**理由**：先寫測試能迫使設計可測試，並提供重構的安全網，從根本降低缺陷與技術債。

### II. Clean Code（程式碼品質）

**程式碼必須清晰、簡潔、易於理解和維護。**

- **有意義的命名**：名稱必須表達意圖；禁止無意義縮寫與單字母變數（迴圈索引除外）
- **單一職責（SRP）**：每個函式、類別只做一件事；服務層、資料模型、UI、工具層邊界不得混用
- **小函式**：函式 SHOULD < 20 行；超過 40 行 MUST 拆分或於 plan.md 的複雜度表中說明
- **低複雜度**：循環複雜度 MUST ≤ 10；巢狀深度 SHOULD ≤ 3，優先使用提前返回（guard clause）
- **DRY 與 YAGNI**：共用邏輯抽取為可重用元件；只實作當前需求，不預留未使用的擴充點
- **註解品質**：程式碼自我解釋，註解說明「為什麼」而非「做什麼」；不保留被註解掉的程式碼
- **明確錯誤處理**：不吞掉例外、不以例外作為流程控制；捕捉具體例外型別並附上可操作訊息
- **無硬編碼**：路徑、超參數、門檻值集中於 `src/config.py`，不得散落於業務邏輯
- **型別與工具鏈**：公開函式 MUST 有型別標註；Black、Ruff、mypy 必須零錯誤

**理由**：Clean Code 降低認知負荷，讓程式碼易於理解、修改與擴展，並減少缺陷。

### III. 測試標準（多層級測試策略）

**完整的測試金字塔確保系統品質。**

- **單元測試（`tests/unit/`，基礎層）**：
  - 測試單一函式或方法的行為，覆蓋所有邏輯分支與邊界條件
  - 每個測試 SHOULD < 100ms，以 mock / stub 隔離 GPU、網路、檔案系統與資料庫
  - 單元測試 MUST NOT 需要 GPU 或下載模型即可執行

- **整合測試（`tests/integration/`，中間層）**：
  - 驗證服務間互動、SQLite 資料流與狀態轉換（下載 → 訓練 → 推論）
  - 需要 GPU 的測試 MUST 以 pytest marker 標示，並可在無 GPU 環境自動略過（此為唯一允許的略過情形）

- **契約測試（`tests/contract/`）**：
  - 驗證 Gradio 事件回應符合 `{status, message, ...}` 格式
  - 契約變更 MUST 同步更新 `specs/*/contracts/` 文件並先於實作修改測試

- **端對端測試**：
  - 針對關鍵使用者流程（模型選擇 → 推論、資料集準備 → 訓練）以小樣本驗證
  - 數量有限，優先以低層級測試取代

- **測試獨立性**：測試之間不得互相依賴或共享可變狀態；結果必須可重現（固定隨機種子）

**理由**：多層級策略在速度與信心間取得平衡，且讓 GPU 昂貴測試不拖慢日常開發迴圈。

### IV. 使用者體驗一致性

**一致、直觀的使用者體驗是不可妥協的要求。**

- **介面一致性**：
  - 所有 Gradio 事件回應 MUST 符合 `{status, message, ...}` 契約
  - 各 Tab 的元件排列、按鈕命名、狀態顯示方式保持一致
  - 介面文字使用繁體中文（台灣用語）

- **錯誤訊息品質**：
  - 訊息必須清晰、可操作，說明發生什麼事與下一步該怎麼做
  - 常見失敗（VRAM 不足、模型不存在、網路中斷、磁碟空間不足）MUST 有對應的友善訊息
  - 不得向使用者暴露原始堆疊追蹤；細節寫入 `logs/app.log`

- **進度與回饋**：
  - 下載、訓練、推論等長時間操作 MUST 顯示進度，並支援取消或背景執行
  - 操作期間 UI 不得凍結，並禁止重複送出

- **文件完整性**：
  - 每項功能需有使用說明與範例；`quickstart.md`、`README.md` 與程式碼同步更新

**理由**：一致的 UX 降低學習曲線、提升信任，並減少支援成本。

### V. 效能要求

**效能是功能的一部分，必須從設計階段開始考慮。**

- **硬體預算（硬性）**：
  - 訓練與推論的 GPU VRAM 使用 MUST ≤ 12GB；啟動訓練前 MUST 先估算並檢查 VRAM
  - 發生 OOM 時 MUST 優雅處理並釋放資源，不得使應用程式崩潰

- **回應目標**：
  - 非模型運算的 UI 互動（切換 Tab、查詢清單、讀取資料庫）p95 < 200ms
  - 推論 MUST 以串流方式輸出，首 token 延遲與 tokens/s 須記錄於基準線
  - 應用程式啟動（不含模型載入）< 5s

- **效能測試**：
  - 為關鍵路徑（模型載入、推論、單步訓練、資料集格式化）建立基準線
  - 效能退步超過 10% MUST 在 PR 中說明原因或修正

- **可觀測性**：
  - 以結構化日誌記錄關鍵操作、耗時與資源使用（含 VRAM 峰值）
  - 偵錯資訊不得顯著影響正常效能

- **優化原則**：先測量再優化，優先處理熱點；避免過早優化，但設計時須考慮資源上限

**理由**：本專案受限於 12GB VRAM，資源預算是可行性條件；從設計階段納入可避免後期重構。

## 品質門檻

所有程式碼合併前必須通過以下門檻：

1. **測試門檻**：
   - `pytest tests/` 全數通過
   - 新增／修改程式碼覆蓋率 ≥ 90%
   - 無被跳過或標記為待辦的測試（GPU 環境缺失之自動略過除外）

2. **程式碼品質門檻**：
   - `black --check`、`ruff check`、`mypy src/` 無錯誤
   - 循環複雜度 ≤ 10 per function
   - 無重複程式碼區塊與未使用的程式碼

3. **效能與資源門檻**：
   - 基準測試無超過 10% 的退步
   - VRAM 估算與實測皆 ≤ 12GB

4. **文件門檻**：
   - 公開函式具備 docstring
   - 使用者可見的變更更新相關文件與 CHANGELOG

## 開發流程

### 1. 功能開發流程

1. **規格階段**：撰寫 spec.md，定義使用者情境與可測試的驗收標準
2. **規劃階段**：產生 plan.md，通過 Constitution Check
3. **測試階段（紅）**：撰寫測試，確認測試因預期原因失敗
4. **實作階段（綠）**：以最小實作使測試通過
5. **重構階段**：在綠燈下重構，維持測試通過
6. **審查階段**：Code review，確認符合本憲章

### 2. 提交紀律

- 測試與其對應的實作 SHOULD 分開提交，或在同一提交內清楚呈現「先測試後實作」的順序，使 TDD 可被稽核
- 每次提交須保持測試為綠燈；重構與功能變更不得混在同一提交

### 3. Code Review 要求

- 所有 PR 必須至少一位審查者核准（單人開發時，由作者以憲章檢核表自審並留下紀錄）
- 審查重點：TDD 流程證據、Clean Code、測試品質與覆蓋率、效能與 VRAM 影響、UX 一致性

### 4. 複雜度管理

- 預設拒絕不必要的複雜度；新增抽象、框架或依賴須證明其必要性
- plan.md 的 Complexity Tracking 表格記錄並證明所有偏離
- 每季審查技術債務與架構決策

## 治理

### 修訂程序

1. **提出修訂**：任何成員可提出建議，說明理由與影響範圍
2. **討論與評估**：評估對現有程式碼、範本與流程的影響
3. **批准**：需專案負責人（或團隊多數）同意
4. **版本更新**：依語意化版本規則更新版本號與修訂日期
5. **同步更新**：更新所有相依範本與文件，並於 Sync Impact Report 記錄

### 版本規則

- **MAJOR**：移除或重新定義原則，向後不相容的治理變更
- **MINOR**：新增原則或實質擴充指導方針
- **PATCH**：澄清、用詞修正、非語意改進

### 合規性審查

- 每個 PR 必須驗證合規性；`plan.md` 的 Constitution Check 為必經關卡
- 每季進行合規性稽核
- 偏離憲章須明確記錄並證明必要性；本憲章優先於個人偏好與臨時決策
